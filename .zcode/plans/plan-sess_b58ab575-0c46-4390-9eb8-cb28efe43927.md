## 问题根因

打包后白屏,由两个独立问题共同导致,根源都在构建配置:

### 根因:`electron.vite.config.ts` renderer 用了 lib 模式

`apps/desktop/electron.vite.config.ts:49-60` 的 renderer 配置:
```ts
build: {
  lib: { entry: "index.html", name: "renderer" },   // ← 问题根源
  rollupOptions: {
    input: { index: resolve("src/renderer/index.html") },
  },
}
```

`lib` 模式会让 Vite 把入口打成 **UMD 库格式**,产物是 `desktop.umd.cjs`(23.9 MB)。但 Electron renderer 是用 `window.loadFile()` 加载的普通网页,**根本不是库**,不应该用 lib 模式。这导致两个直接错误:

1. **`<script type="module" src="./desktop.umd.cjs">` 加载失败**(对应你报的第二个错):UMD 不是 ESM,且 `.cjs` 扩展名在 `file://` 协议下 MIME 是 `text/plain`,触发 "Strict MIME type checking is enforced for module scripts",脚本被拒绝执行。

2. **inline script 被 CSP 拦截**(对应你报的第一个错):`index.html` 里第 16-25 行有一段 FOUC guard inline script(读 `prefers-color-scheme` 给 `<html>` 加 `.dark` class)。生产环境 `index.ts:36-47` 启用了严格 CSP `script-src 'self'`,inline script 被拒。报错 hash `sha256-Rehz3k...` 正对应这段。

   注意:这个 CSP 拦截在 dev 模式也存在(CSP 是 prod-only,dev 不开),但 dev 模式下 Vite 的 HMR/client 脚本本身也有 inline,且 React 能正常挂载所以看不到影响。真正让白屏"显形"的是问题 1 —— lib 模式让主入口脚本完全加载失败。

## 修复方案

### 改动 1(核心):去掉 renderer 的 lib 模式

**文件:`apps/desktop/electron.vite.config.ts:49-60`**

把 `build.lib` 整段删掉,只保留 `rollupOptions.input`。这样 Vite 走标准 app 模式,入口 `index.html` 产出正常的 ESM `<script type="module" src="./assets/index-xxx.js">`,MIME 正确、CSP `'self'` 允许。

```ts
renderer: {
  root: "src/renderer",
  build: {
    rollupOptions: {
      input: { index: resolve("src/renderer/index.html") },
    },
  },
  // ... 其余 resolve / optimizeDeps / plugins / worker 配置不变
}
```

同时删掉原 `lib` 上方那段已失效的注释(第 52-55 行关于 "name is required by Vite when a lib entry..." 的注释),因为不再用 lib 模式。

### 改动 2:消除 inline FOUC script,改用 CSP 友好的方式

**文件:`apps/desktop/src/renderer/index.html`**

删掉第 16-25 行的 inline `<script>`,改用两种 CSP 兼容的方式之一来避免主题 FOUC:

- **方案 A(推荐,最小改动)**:把 FOUC 逻辑移到 `renderer/lib/theme.ts` 导出的一个独立模块,由 `main.tsx` 在 `ReactDOM.render` 之前同步调用。由于 main.tsx 产物是外部 ESM 脚本(`'self'` 允许),CSP 不拦。
  - 具体:在 `theme.ts` 里加一个 `initFoucGuard()` 函数,内容就是原 inline script 的逻辑(读 `prefers-color-scheme` → `classList.add('dark')`);在 `main.tsx` 顶部、`createRoot` 之前调用它。
  - 理由:main 进程 `initTheme()` 已在 `whenReady` 时设了 `nativeTheme.themeSource`,Chromium 的 `prefers-color-scheme` 在页面加载时已就绪,所以外部脚本同步读 media query 一样能拿到正确值,FOUC 防护效果与 inline 版本一致。

- **方案 B(备选,不改 JS)**:保留 inline script,但在 CSP 的 `script-src` 里加该脚本的 hash `'sha256-Rehz3kJeGMad8rFut/jdZX5pgrLF+DKN+rP7R3P9kG8='`。
  - 缺点:hash 脆弱——改一行 script 内容 hash 就变,得同步改 CSP,维护成本高。

我采用**方案 A**。

### 改动 3:把 renderer 的 console-message 也写入 main.log(顺手改进,可选)

**文件:`apps/desktop/src/main/window.ts:84-93`**

当前 renderer 的 `console-message` / `did-fail-load` / `render-process-gone` 只 `process.stderr.write`,打包后 stderr 无处可去,白屏诊断困难。改成同时调用 `log.error(...)` 落盘到 `main.log`,这样以后白屏直接看 `%APPDATA%\Mcode\logs\main.log` 即可。

这一项是顺手改进,与白屏修复无直接关系,但能大幅降低未来同类问题的排查成本。如果你不想要这个改动,我可以只做改动 1+2。

## 验证步骤

1. `cd apps/desktop && npx tsc --noEmit -p tsconfig.json` —— 类型检查
2. `NODE_OPTIONS=--max-old-space-size=4096 npx electron-vite build` —— 重新构建(renderer 产物会变成 `out/renderer/index.html` + `out/renderer/assets/*.js`,不再有 `desktop.umd.cjs`)
3. 检查 `out/renderer/index.html`:确认 `<script>` 是 `type="module" src="./assets/index-xxxx.js"`(ESM、`'self'` 允许),且无 inline script
4. `pnpm package` 重新打包,安装后打开,应正常显示(可用方法 B 从命令行启动 exe 看 stderr 确认无 `[renderer:ERROR]`)
