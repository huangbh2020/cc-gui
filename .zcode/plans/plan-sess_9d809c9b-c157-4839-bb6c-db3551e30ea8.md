# 方案 E 实施计划：本地协议翻译层（Anthropic ↔ OpenAI）

## 架构总览

在 main 进程内起一个本地 HTTP server（翻译层），伪装成 Anthropic `/v1/messages` 端点。Claude 二进制通过 `ANTHROPIC_BASE_URL` 指向它，它把 Anthropic 协议请求翻译成 OpenAI `/v1/chat/completions` 发给真实端点，响应再反向翻译成 Anthropic SSE 流回 Claude 二进制。

```
Claude 二进制 ──Anthropic /v1/messages──▶ 翻译层(127.0.0.1:<port>)
                                            │ ① 请求翻译: content blocks→messages, tools→functions
                                            │ ② fetch 真实 OpenAI 端点
                                            │ ③ 响应翻译: OpenAI SSE chunks→Anthropic SSE 事件
                                            ▼
                                   OpenAI / Azure / vLLM / 聚合网关
```

**核心洞察**：`customEnv.ts` 已把 tier→真实模型名映射好，翻译层收到的请求 `model` 字段就是用户配的真实模型名（如 `gpt-4o`），所以**翻译层只做协议格式翻译，不做模型名翻译，直接透传 model**。

**对现有链路透明**：在 `RuntimeManager.sendTurn` 把 OpenAI 配置的 `apiConfig` 改写为 `{baseUrl: "http://127.0.0.1:<port>", authToken: <内部路由标识>, ...原配置}`，下游 `buildCustomEnv` / `settingSources` / 诊断日志**全部原样工作**，无需改 `customEnv.ts`。

## 翻译规格（核心契约）

**请求翻译（Anthropic → OpenAI）**：
- `model` 直接透传（customEnv 已映射好）
- `system` → 首条 `{role:"system"}` 消息
- `tool_use` block（assistant）→ `tool_calls[].function.arguments = JSON.stringify(input)`
- `tool_result` block（user）→ 独立 `{role:"tool", tool_call_id}` 消息
- `tools[].input_schema` → `tools[].function.parameters`；`tool_choice` auto/any/tool/none → `"auto"`/`"required"`/`{type:"function",function:{name}}`/`"none"`
- `thinking` / `cache_control` 丢弃；`max_tokens`/`temperature`/`top_p`/`stop_sequences` 透传

**响应翻译（OpenAI SSE → Anthropic SSE）状态机**：
- 首个 chunk → `message_start`（usage 全 0）
- `delta.content` → `content_block_start`(text) + `content_block_delta`(text_delta)
- `delta.tool_calls[].id`+`name` → 关闭前块 + `content_block_start`(tool_use)
- `delta.tool_calls[].function.arguments`（增量）→ `content_block_delta`(input_json_delta, partial_json) ← **最易错点**
- `finish_reason` → 关闭所有块 + `message_delta`(stop_reason 映射 + usage) + `message_stop`
- stop_reason 映射：stop→end_turn, tool_calls→tool_use, length→max_tokens, content_filter→refusal
- **不发 ping**（SDK 客户端丢弃）；**不合成 thinking 块**（OpenAI 无 signature）

**认证**：翻译层忽略 Claude 二进制发来的内部标识头，用用户配置的真实 token 向 OpenAI 端点发 `Authorization: Bearer`（Azure 按 host 判断，加 `api-version` + `api-key` 头）。

## 模块划分

新增（`apps/desktop/src/main/providers/bridge/`）：`types.ts`、`requestTranslator.ts`、`responseTranslator.ts`、`bridgeServer.ts`、`bridgeRegistry.ts`

**关键接口**：
```ts
interface BridgeHandle { localUrl: string; routeToken: string; close(): void; }
async function startBridge(upstream: ApiConfig): Promise<BridgeHandle>;
class BridgeRegistry {
  acquire(customModelId, upstream): Promise<BridgeHandle>;  // 引用计数复用
  release(customModelId): void;
  static disposeAll(): void;  // before-quit 调用
}
```

**改动点**：
1. `contracts/customModel.ts` + `ipc.ts`：加 `Protocol` 类型 + `protocol?` 字段 + `ProtocolSchema`
2. `secretStore.ts`：加 `resolveProtocol`（default `"anthropic"`），透传字段 + 旧数据迁移
3. `RuntimeManager.ts`（第172行后）：`if (cfg.protocol==="openai")` 启动 bridge、改写 apiConfig
4. `ipc/customModel.ts`：probe 加 OpenAI 分支（直接 fetch）
5. `main/index.ts`：before-quit 加 `BridgeRegistry.disposeAll()`
6. `CustomModelsPanel.tsx`：加"API 格式"下拉 + OpenAI 模式提示/一键填充
7. `ModelDropdown.tsx`：可选 badge

**不需改**：customEnv.ts、ClaudeAgentSdkProvider、preload、SdkMessageAdapter、sessionStore。

## 分阶段实施（POC 先行）

- **阶段0**（~0.5天）：protocol 字段贯通 contracts→secretStore→ipc→UI（默认 anthropic，行为不变）
- **阶段1**（~2-3天，POC）：翻译层核心 + 纯对话跑通（先不实现 tool_use）。**验证最大未知**
- **阶段2**（~3-4天）：tool_use/tool_result/tools/tool_choice + tool_calls 流式分片状态机 + thinking 丢弃，跑通工具调用
- **阶段3**（~1-2天）：UI 下拉 + probe 双路径 + badge
- **阶段4**（~2-3天）：联调(OpenAI官方/Azure/聚合网关) + 并发验证 + 写 docs/openai-bridge.md

**合计约 1.5-2 周**。

## 测试策略
- 翻译层单元测试：用真实录制的 OpenAI SSE chunk 序列断言产出的 Anthropic 事件序列，重点覆盖 tool_calls 分片拼接、多 block 编排、stop_reason 映射
- 端到端：阶段1/2/4 各有"跑通"目标
- 回归：Anthropic 路径完全不受影响

## 主要风险与对策
- tool_calls 流式分片拼接错误 → 状态机 + 单元测试 + 真实流量回归
- Azure 形态差异（api-version/api-key）→ 按 host 分支，阶段4 专项联调
- OpenAI 模型对 Claude 风格 system prompt/工具的适配 → 模型能力问题非架构问题，GPT-4o 系列实测良好
- thinking 签名无法合成 → 已定策略：丢弃 thinking，可接受
