# AskUserQuestion 交互 —— 先 dump 验证机制(同 P3 模式)

## 需求
模型用 AskUserQuestion 工具向用户提问时,在输入框上方弹框让用户确认/输入。

## 核心未知点(必须 dump 确认)
本机 claude 2.1.186 + stream-json 下,AskUserQuestion 的机制完全未知。可能性:
1. **控制协议**(control_request)—— P3 已验证 2.1.186 不生效,大概率排除
2. **工具调用**:模型 emit AskUserQuestion 的 tool_use,但单向 `-p` 模式无法等用户回答 → 可能跳过/拒绝
3. **无真正交互**:claude 在 result 文本里说"需要你回答",用户下一条消息回答(无阻塞)

这和 P3 是同类问题(双向交互),P3 教训:不基于猜测写代码,先真实 dump。

## 本阶段计划(验证)
1. 用一个明确要求"向用户提问 3 个选项让用户选"的 prompt,在 default 模式跑 dump
2. 看 stdout 是否有 AskUserQuestion 工具调用、control_request、或别的特殊事件
3. 关键判断:claude 是否**阻塞等待**用户回答(那需要 stdin 写入),还是直接跳过/用文本兜底
4. 若阻塞 → 验证 stdin 写入格式(像 P3 试 control_response)
5. 若不阻塞/不支持 → 明确告知,讨论降级方案(如把问题渲染成可点击的建议,用户回答走下一条消息)

## 决策依据
dump 结果决定一切:
- 若机制可用且能 stdin 回答 → 实现真正的弹框交互(改 spawn 为双向、解析事件、写 stdin)
- 若机制不可用(如 P3 那样)→ 降级:解析出问题文本,渲染为建议气泡,用户回答作为下一条 prompt(非阻塞,但至少把问题可视化)

## 涉及文件(验证后确定)
预期 ClaudeRuntime(解析/stdin)、sessionStore(状态)、ChatPane(弹框 UI)。具体待 dump。

## 风险
- 高概率机制不可用(同 P3):本机 2.1.186 非交互模式对交互类工具支持有限
- 即使机制可用,改 spawn 为双向 stream-json 是较大改动,且 stdin 生命周期管理复杂

是否批准先做 dump 验证?(只读性质,不改项目代码)
