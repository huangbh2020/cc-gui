## 背景与根因(已查实)

报错 `bridge: upstream fetch failed: fetch failed` 来自 `apps/desktop/src/main/providers/bridge/bridgeServer.ts:196`。OpenAI↔Anthropic 桥接器对上游 `http://120.77.13.237:3099/v1` 的 `fetch()` 在传输层被拒。日志交叉验证结论:

- 同一个桥接器、同一个 URL 在 **2026-08-03** 能正常连到上游(每个请求都拿到真实 503 响应),当天 0 次 `fetch failed`。
- 从 **2026-08-05** 起,217 次 MiniMax 请求全部 `fetch failed`,0 次成功。
- **今天** 从同一台机器用 `curl` 和系统 Node `fetch` 直连该 URL 都成功(47ms 连接、返回 401)。服务器在线、系统网络可达。
- 8-03 到 8-05 之间 `bridgeServer.ts` 唯一改动是加了无关的 `stream_options`。

→ 结论:**App 进程级别的网络环境问题**(VPN/网络栈/防火墙/Electron net 会话),不是代码 bug。但桥接器有两个代码层缺陷让这个问题无法被定位、无法自愈:

1. **`err.cause` 被丢弃**:`log.error("...fetch failed: " + err.message)` 只拿到 undici 抛的外层 `TypeError.message`(恒为字符串 `"fetch failed"`),真正的错误码(`ECONNREFUSED`/`UND_ERR_CONNECT_TIMEOUT`/`ECONNRESET` 等)藏在 `err.cause` 里,从未被记录或透传。
2. **零重试**:传输层瞬时失败(很常见——尤其是公网 IP + 非标端口 3099)直接返回 502,Claude 二进制看到错误后用自己的退避重试,但每次重试都撞同一面墙。

## 修改方案

只动 `apps/desktop/src/main/providers/bridge/bridgeServer.ts` 一个文件,三处改动。

### 改动 1:提取并丰富错误原因(诊断核心)

新增一个工具函数 `describeFetchError(err): string`,从 undici 的 `TypeError` 里挖出真实原因:

```ts
function describeFetchError(err: unknown): string {
  const e = err as { message?: string; cause?: { code?: string; name?: string; message?: string } };
  const cause = e?.cause;
  const code = cause?.code || cause?.name;
  // cause.message 形如 "connect ECONNREFUSED 120.77.13.237:3099" —— 比 "fetch failed" 有用得多
  return code ? `${code}: ${cause?.message ?? e?.message}` : (e?.message || String(err));
}
```

### 改动 2:加一次自动重试(针对瞬时传输失败)

把 `handleMessages` 里的单次 `fetch` 抽成 `fetchUpstream(url, opts, ac)` 并加重试循环:

- **只重试传输层抛出的错误**(catch 到的 reject),不重试 HTTP 状态码错误(那些走 `!upstreamRes.ok` 分支,503/4xx 各有各的语义)。
- **重试条件**:用 `describeFetchError` 判断错误码属于可重试集合 —— `ECONNRESET`/`ECONNREFUSED`/`EAI_AGAIN`/`UND_ERR_CONNECT_TIMEOUT`/`UND_ERR_SOCKET`。`ECONNREFUSED` 理论上重试也没用,但端口 3099 在公网路由恢复后能自愈,保留它无害(重试上限 1 次很快就返回)。
- **重试次数**:最多 **1 次额外尝试**(即总共 2 次),间隔 **500ms**(`setTimeout` + `await`,尊重 `ac.signal`,被 abort 时立即抛出不再重试)。
- **日志**:每次失败 `log.warn` 带真实 cause;最终失败才 `log.error`。

### 改动 3:把真实原因透传给前端(替代 `fetch failed`)

`sendError(res, 502, ...)` 的 message 从 `upstream unreachable: ${msg}` 改成 `upstream unreachable: ${describeFetchError(err)}`。这条 message 经 Claude 二进制 → SdkMessageAdapter 的 error result 分支(`SdkMessageAdapter.ts:1137-1146`)已经会显示给用户,所以无需改前端——用户看到的错误从 "upstream unreachable: fetch failed" 变成可读的 "upstream unreachable: ECONNREFUSED: connect ECONNREFUSED 120.77.13.237:3099"。

## 不做的事

- **不改网络层实现**(不换 `node:http`、不引入 Agent/ProxyAgent):根因是环境,代码层先让诊断和重试到位;若重试后 cause 显示是代理/超时类问题,再单独决定要不要换栈。
- **不动 RuntimeManager / customEnv / git.ts**:这些路径都对(`baseUrl` 重写到 `127.0.0.1:<port>` 是对的),错误只在桥接器出站那一步。
- **不改前端**:错误展示链路已经通,只是消息内容变可读。

## 验证

1. `cd apps/desktop && npx tsc --noEmit -p tsconfig.json` 通过。
2. 重启 `pnpm dev`,复现一次 MiniMax 请求:日志里应出现 `bridge: upstream retrying after <真实 cause>`(若重试)和最终 `bridge: upstream fetch failed: <真实 cause,不再是裸 "fetch failed">`。
3. 拿到真实 cause 后即可对症:如果是 `UND_ERR_CONNECT_TIMEOUT` → app 进程到该公网 IP 的路由被掐(查 VPN/防火墙);如果是 `ECONNREFUSED` → 服务端临时关停;如果是代理类错误 → 考虑后续加 ProxyAgent。
