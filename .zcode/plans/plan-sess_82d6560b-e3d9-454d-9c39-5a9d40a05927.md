# 让聊天线程配置真正变成「线程内部」的状态

## 目标

用户在 A 线程发起的聊天不应受切到 B 线程或新建 B 线程影响;
在 B 线程修改模型 / 思考级别 / 权限模式等,也不应回写到 A 线程或影响其他线程。

数据层(DB、Session 类型、RuntimeManager、SDK provider)其实**已经按线程持久化**了 —
`sessions` 表的 `model / effort / permission_mode / custom_model_id` 列就是每个线程独立存的,
`ClaudeAgentSdkProvider.startTurn` 也只读 `session.{model,effort,permissionMode,customModelId}`
(RuntimeManager.ts:115-140) 发到 SDK。
`SESSION_UPDATE_SETTINGS` IPC 通道、preload 暴露、main 端处理、repo `updateSettings` 也都写好了,
只是渲染层没人调用它。

**唯一要改的就是渲染层的 Zustand store + 几个 UI 消费点**,让前端跟后端一样按线程视图化。
下面分 4 块,按依赖顺序给出最小、确定可执行的实现。

---

## 设计要点(先讲为什么这么改)

1. **状态模型采用「单 slot + 同步水合」** 而不是 `Record<sessionId, …>`。
   - `Record<sessionId, ...>` 在 Zustand 下会引发大范围选择器重写,改造成本高,Selector 一处漏改就会无限循环(已踩过);
   - 「单 slot + `selectSession` 时把活跃 session 的行字段读进 slot」改动集中在 store 内部,
     现有 `setEffort`/`setModel`/`setPermissionMode`/`setCustomModel` 调用点**完全不动**,
     组件侧零感知,StatusBar / ComposerToolbar 不用改。
2. **per-session `isRunning`**:改成 `runningBySession: Record<sessionId, boolean>`。
   否则 B 线程正在跑时切到 A 线程,会看到「working」徽标属于 A;更严重的 — A 线程想发消息会被 `get().isRunning` 拦截。
   其他已带 `sessionId` 的 pending 字段(pendingQuestion / pendingApprovals / turnFiles)保持现状,
   渲染时按 activeSessionId 过滤(已经是这个写法,行为不变)。
3. **每次 chip 改动立即落库**(用已经写好但没被调用的 `session.updateSettings`),
   避免「当前线程改了切走,再切回来又变成别人」的状态不一致。落库是 fire-and-forget,不影响 UI 响应。
4. **新线程默认值**:沿用「创建时 session 拿到 model/effort/permission/customModelId」— 现在已经从全局 slot 拿,
   只要新线程在创建时复用 *当前活跃线程* 的值(而不是「上次手动改过但没存」的值),语义最自然:
   这条已经在 `startSession` 里从 `get().model/effort/permissionMode/customModelId` 拿,无需改 — 因为 slot 永远代表活跃线程的视图。

## 改动清单(按文件)

### 1. `apps/desktop/src/renderer/stores/sessionStore.ts` — 核心

#### 1.1 状态字段

- 保留: `permissionMode`、`model`、`customModelId`、`effort`(作为当前活跃线程的视图 slot)。
- 替换 `isRunning: boolean` → `runningBySession: Record<string, boolean>`。
  - 默认 `{}`。
  - 提供 selector `isRunning` 通过 `activeSessionId` 派生(下文 1.5)。

#### 1.2 新增内部 helper:`syncConfigFromSession(sessionId)`

从 `sessionsByProject[projectId].find(s => s.id === sessionId)` 读出 `model/effort/permissionMode/customModelId`,
写入全局 slot。如果找不到或 session 不存在,不动 slot(避免初次进入时清空默认值)。

#### 1.3 `selectSession(sessionId)` 改造

```ts
selectSession: async (sessionId) => {
  // 1) 切 slot:把目标 session 的持久化配置读到全局视图
  syncConfigFromSession(sessionId);
  // 2) 切活跃 id + 清掉跨线程杂项(原逻辑保持)
  set({ activeSessionId: sessionId, pendingApprovals: [], pendingQuestion: null, turnFiles: [] });
  // 3) 消息懒加载
  if (get().messagesBySession[sessionId]) return;
  const { messages } = await api.session.messages({ sessionId });
  set((s) => ({ messagesBySession: { ...s.messagesBySession, [sessionId]: fromRecords(messages) } }));
};
```

(同时 `selectProject` 间接走 `selectSession`,自动获益。)

#### 1.4 `setPermissionMode` / `setModel` / `setEffort` / `setCustomModel` 改造

- 先就地更新全局 slot(原行为,UI 立刻反映);
- 取 `activeSessionId`,非空则 fire-and-forget `api.session.updateSettings({ sessionId, model?, effort?, permissionMode?, customModelId? })`。
  - 失败仅 `console.error`,不撤回 UI(用户已看见;后端是 source of truth,下次 `selectSession` 会同步过来)。
  - 成功返回的 session 不需要再 merge — 我们下次切换时会再读;但 `sendTurn` 拿到最新 session 的 merge 路径仍要保留(它走 `get().sessionsByProject[pid]` 替换,已存在)。
- `setCustomModel` 现在同时改 `customModelId` + `model` 两个字段,两条 update 合并成一个 patch 调用。

#### 1.5 `sendPrompt` 改造

- 入口护栏:把 `get().isRunning` 改为 `get().runningBySession[sessionId] === true`,这样其他线程正在跑不影响本线程发送。
- 启动时: `set((s) => ({ runningBySession: { ...s.runningBySession, [sessionId]: true } }))`。
- 不再向 `claude.sendTurn` 重复带 `model/effort/permissionMode/customModelId` 覆盖 — 这些字段已经通过 `setX` → `updateSettings` 写进了行,`RuntimeManager.sendTurn` 会从行里读真值。
  - 保留: 不传覆盖字段,`SendTurnSchema` 都是 optional,zod 通过,语义更干净。
  - 替代:删除 `ipc/claude.ts:90-99` 中「在内存中应用 input 覆盖」的代码,因为 UI 端已经先 persist(去除重复代码;但保留无害,我倾向 **保留 main 端覆盖逻辑作为兜底**,只删 renderer 端重复发送)。
- main 返回的 `session` 用同样 patch merge 进 `sessionsByProject`(原逻辑保留)。

#### 1.6 `ingestEvent` 改造

- `e.type === "turn.done" / "error"` / `interrupt`:把 `isRunning: false` 替换为
  `runningBySession: { ...s.runningBySession, [sid]: false }`。
- `e.type === "question.ask"`: `set({ pendingQuestion: { sessionId: sid, ... } })`(已有)。
- `e.type === "approval.request"`:已有,继续推到全局队列(渲染端按 activeSessionId 过滤)。
- 新增:`e.type === "turn.started"`(可选,见 § 3)— 设为 `runningBySession[sid]=true`,
  这样「真·开始跑」的精确时刻由后端事件驱动,而不是 `sendPrompt` 的乐观置位,减少边界。
  - 若不引入 turn.started,保留乐观置位也没问题(后端 turn.done 会纠正)。
- `pendingQuestion` 不变(已经带 sessionId);`pendingApprovals` 不变;`turnFiles` 不变(渲染时按 activeSessionId 过滤;若想更严格,可加 `turnFilesBySession`,但目前行为已对,不在本任务范围)。

#### 1.7 新增 selector(对外暴露的派生)

```ts
const isRunning = useSessionStore((s) =>
  s.activeSessionId ? !!s.runningBySession[s.activeSessionId] : false,
);
```

下游 `ChatPane`、`StatusBar` 改用此 selector(见 § 2)。

#### 1.8 `init` 末尾

- `init` 已经在 `firstSession` 存在时 `await selectSession(firstSession.id)`,由于 `selectSession` 现在调用 `syncConfigFromSession`,首启自动拿到第一线程的真实配置。
- 兜底:若没有 firstSession,保留 `permissionMode: "default", model: "default", effort: "high", customModelId: null` 的当前默认(继续 `isRunning: false` → `runningBySession: {}` 即可)。

### 4. `apps/desktop/src/main/ipc/claude.ts` — 简化(可选,推荐做)

`CLAUDE_SEND_TURN` 中 `if (input.model !== undefined) updated = ...` 这段(in-memory override merge)
只在「renderer 忘记先 updateSettings」时才有意义;若 §1.4 让 UI 端强制先 updateSettings 再 sendTurn,
这段就是冗余。两种选择:
- **A 保守(推荐)**:保留 main 端 merge,但去掉写库那段里的 `SessionRepo.updateCustomModelId` —
  既然 §1.4 已经写过了。这里只是补强「同一时间窗内兜底」。
- **B 激进**:完全删除 in-memory override merge(`input.model` 等不再影响 `Session`,
  以 DB 行为准)。需把 §1.4 的 updateSettings 设为 await 后再 sendTurn,否则会出竞态。
- 本计划选 **A**:风险最低,行为与现状一致(只是把「在 main 端也写库」的 customModelId 写库交给 §1.4 的 updateSettings)。

## 验收场景(自动 + 手动)

- **自动(类型 + 构建)**:
  1. `cd apps/desktop && npx tsc --noEmit -p tsconfig.json` 0 错。
  2. `pnpm -w typecheck`(若有) 0 错。
- **手动**:
  1. 启动 dev,在 A 线程选 `Sonnet + Plan`,发一条消息确认在跑。
  2. 不停,点 B 线程(或新建):ComposerToolbar 应显示 B 的真实配置(Sonnet/Opus + Auto + Default 等),B 的输入框**可输入可发送**(不卡 isRunning)。
  3. 在 B 线程把模型改成 Opus、Effort 改 Low、Permission 改 Bypass。
     切回 A 线程:ComposerToolbar 仍显示 A 的 `Sonnet + Plan`,且 A 的运行不受影响。
     再切回 B:显示 `Opus + Low + Bypass`。
  4. 退出应用重启:每个线程的 chip 仍是当时自己设的值(走 `updateSettings` 已落 DB)。
  5. 左栏「+ 新建线程」时,新线程的初始 chip 等于**当前活跃线程**的配置(因为 `startSession` 从全局 slot 拿,而 slot = activeSession 的视图)。符合用户「B 线程修改不影响其他线程」,但同时不强制每次新建都是 default。

## 风险与回退

- **风险 1**:Zustand selector 误改返回新引用导致无限循环。已规避 — `runningBySession[id]` 是 boolean,`Object.is` 安全。
- **风险 2**:`selectSession` 的 `syncConfigFromSession` 在 `init` 阶段 `sessionsByProject` 还没填充完时调用,导致读到旧值。已规避 — `init` 走 `Promise.all` 全部 `await` 后才设置,且 `selectSession` 内部走 `get().sessionsByProject` 查找;首条线程的 chip 渲染时已经能从 store 读到正确的 model。
- **回退**:所有改动集中在 `sessionStore.ts` + 两处 `isRunning` 替换;若出现回归,
  把 `isRunning` 字段加回去、把 `runningBySession` 删掉即可恢复(语义回到 PR 之前)。
