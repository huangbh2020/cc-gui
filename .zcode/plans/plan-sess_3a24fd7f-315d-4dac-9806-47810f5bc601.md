## 问题

中间面板流式输出 markdown 内容时,出现延时渲染:流式过程中只显示纯文本(无格式),直到整个 turn 结束(`turn.done`)才突然整体切换为 markdown 渲染。

## 根因

`apps/desktop/src/renderer/components/chat/MessageBlocks.tsx:238-263` 的 `BlockView` text 分支有两个短路条件,叠加导致 markdown 在整个流式期间完全不渲染:

```tsx
const deferredText = useDeferredValue(block.text);
const isStale = deferredText !== block.text;

if (isStreamingTail || isStale) {
  return <div className="whitespace-pre-wrap ...">{block.text}</div>;  // 纯文本
}
return <Markdown>{deferredText}</Markdown>;
```

1. **`isStreamingTail` 恒真**:`ChatPane.tsx:256` 中 `isStreamingTail = isRunning && m.role === "assistant" && i === messages.length - 1`。只要 turn 在跑,最后一条 assistant 消息该标志恒为 true → 整个流式过程永远走纯文本分支。直到 `turn.done` → `isRunning` 翻 false → 才切到 `Markdown`,这就是"结束才渲染"的来源。

2. **`isStale` 兜底**:`useDeferredValue` 的 deferred 值在高频 delta 下持续滞后,`isStale` 长期为 true,即便去掉 `isStreamingTail` 也仍走纯文本。

这是故意的性能优化(避免 60Hz 每帧解析 markdown + Shiki),但权衡失衡,牺牲了实时性。

## 修复方案

**核心改动:移除纯文本短路,始终用 `deferredText` 渲染 `Markdown`,让 `useDeferredValue` 自然节流。**

- `block.text` 每帧变化(实时),`deferredText` 由 React 在空闲时更新(天然节流,约每 50-100ms 一次而非每帧)。
- `Markdown` 是 `memo` 组件,`deferredText` 引用不变就不重渲染 → 不会每帧全量解析。
- 流式期间 markdown 以"稍滞后于实时"的节奏**渐进呈现**,结束时自然收敛,不再有"突然切换"的延时感。
- `isStreamingTail` 仍保留用于尾部 spinner 等其它逻辑(本改动不动 `ChatPane.tsx`),只是 `BlockView` 的 text 分支不再用它做 markdown 短路。

## 具体改动

### 文件:`apps/desktop/src/renderer/components/chat/MessageBlocks.tsx`

`BlockView` 的 text 分支(238-263 行)改为:

```tsx
case "text": {
  // useDeferredValue throttles the markdown re-parse: `block.text` updates
  // every delta (~60 Hz) but `deferredText` only advances when React has
  // idle time, so <Markdown> (memoized) re-renders at a paced cadence
  // instead of every frame. Markdown thus appears progressively during
  // streaming and converges naturally when the turn ends - no more
  // "raw text until done, then flip to markdown" delay.
  // eslint-disable-next-line react-hooks/rules-of-hooks
  const deferredText = useDeferredValue(block.text);

  // Streaming tail (still receiving deltas): keep the deferred value fresh
  // enough to feel live, but let Markdown render it progressively. We no
  // longer fall back to raw whitespace-pre-wrap for the whole turn - that
  // caused the perceived "markdown delay". Shiki highlighting of code blocks
  // is itself deferred inside <Markdown> (lazy highlighter + cache), so the
  // expensive path is already guarded.
  return <Markdown>{deferredText}</Markdown>;
}
```

要点:
- 删除 `isStale` 变量与 `if (isStreamingTail || isStale)` 纯文本分支。
- 保留 `useDeferredValue(block.text)` 作为节流手段(关键:它让 `Markdown` 的 memo 在 delta 高频期仍能命中,避免每帧重解析)。
- `isStreamingTail` 参数保留(其他 block 类型、`MessageRow` 的 spinner 仍用它),只是 text 分支不再依赖它。

### 不需要改动的部分

- `ChatPane.tsx`:`isStreamingTail` 的计算和透传保持不变(尾部 spinner 仍需要)。
- `Markdown.tsx`:Shiki 高亮已是"延迟高亮"模式(懒加载 highlighter 单例 + LRU 缓存 + `useMemo` 依赖 `rawCode`),流式期间代码块会先用 `childProps.children` 纯文本回退(`pre` 分支 234-238 行 `html` 为 null 时),highlighter 就绪/缓存命中后才注入高亮 HTML → 天然符合"延迟高亮,实时解析"。
- `sessionStore.ts` 的 delta flush 节流:不动,它负责合并高频 delta 为每帧一次 setState,与本改动正交。

## 验证

1. 类型检查:`cd apps/desktop && npx tsc --noEmit -p tsconfig.json`(确认删除 `isStale` 后无未使用变量报错,`isStreamingTail` 仍作为 props 使用)。
2. 手动验证(`pnpm dev`):发起一个会产生 markdown(标题、列表、代码块、表格)的 turn,观察:
   - 流式过程中标题/列表/加粗等应**实时**以 markdown 格式呈现(稍有节流滞后,但不卡顿)。
   - 代码块流式时先以纯文本显示,稳定后转为高亮(延迟高亮)。
   - turn 结束时无"突然整体切换"的闪烁,内容平滑收敛。
3. 回归:确认历史消息(非流式)markdown 渲染不受影响(`deferredText === block.text`,`Markdown` 正常渲染)。

## 风险与权衡

- **性能**:流式期间 `Markdown` 会被以 ~10-20Hz 的节奏重新解析(由 `useDeferredValue` 节流,非每帧)。对长输出(几千行 markdown)可能略增 CPU。但 `Markdown` 的 `memo` + `useDeferredValue` 双重保护,实际重解析频率受控;且现代机器解析常见 markdown 段落开销很小。Shiki 高亮仍由其内部缓存保护,不会随文本增长反复全量高亮同一代码块。
- **替代方案**:若后续发现长输出卡顿,可引入段落级增量 markdown(按 block 拆分,只重渲染变化段),但那是更大重构,本次不做。
