# 修复 Plan Mode 模式同步 + 计划批准悬浮框（含通用工具审批 UI）

## 背景与根因

**问题1（模式不同步）**：`ComposerToolbar` 显示的 `permissionMode` 是 store 里的全局"下一个会话"设置。当模型在对话中主动调用 `EnterPlanMode` 工具进入计划模式时，**没有任何事件通知前端**，composer chip 和 StatusBar 都不会同步切换到 Plan。

**问题2（对话卡死）**：模型在 plan 模式完成规划后调用 `ExitPlanMode` 工具等待批准。当前这个工具走 `canUseTool → requestApproval → approval.request` 事件，但 **renderer 完全没有 approval UI**（grep 确认零处理）。所以不仅 ExitPlanMode 卡住，default 模式下需要审批的 Bash/Edit 等也会卡——这是 P3 的前端遗留缺口。

**SDK 行为确认**（来自 Snowflake 官方文档）：
- `ExitPlanMode` 的 `input.plan` 包含计划文本（类型 .d.ts 不完整但运行时确实有）
- 批准：`{behavior:"allow", updatedInput:{message}}` → SDK 自动结束当前 turn 的 plan mode，后续回到 default
- 拒绝：`{behavior:"deny", message}` → 保持 plan mode，模型可修改后重新请求批准
- `EnterPlanMode` input 为空，仅作为"模型已进入 plan 模式"的信号

## 设计思路

照搬项目里最成熟的 **AskUserQuestion 端到端链路**（canUseTool 拦截 → ApprovalBridge Deferred → 专用 IPC 通道 → 悬浮卡片 UI）。新增两条对称的链路：ExitPlanMode 批准、通用工具审批。模式同步则通过在 `handleAssistant` 里识别 `EnterPlanMode`/`ExitPlanMode` tool_use 发新事件。

## 实施步骤

### 第1步：扩展契约（`packages/contracts/src/`）

**`runtime.ts`** — 新增 3 个 RuntimeEvent 类型 + 加入联合：
```ts
// 模式切换通知（问题1核心）
export interface ModeChangeEvent {
  type: "mode.change";
  sessionId: string;
  mode: PermissionMode;        // "plan" | "default" | "acceptEdits"
  source: "model" | "user";    // 谁触发的（model = EnterPlanMode/ExitPlanMode 工具）
}

// 计划批准请求（问题2核心）
export interface PlanApprovalRequestEvent {
  type: "plan.approval_request";
  sessionId: string;
  requestId: string;
  toolCallId: string;
  plan: string;                // 计划文本（来自 input.plan）
}
```
复用现有 `ApprovalRequestEvent` 处理通用工具审批（不新增类型，只是前端终于开始消费它）。

**`provider.ts`** — 新增 ProviderContext 方法 + 决策类型：
```ts
export interface PlanApprovalRequest {
  requestId: string;
  plan: string;
  toolUseId?: string;
}
export interface PlanApprovalDecision {
  approved: boolean;
  /** 用户编辑后的计划；approved 时通过 updatedInput 回写 */
  editedPlan?: string;
  /** 拒绝时的反馈理由 */
  reason?: string;
}
export interface ProviderContext {
  // ... 现有
  requestPlanApproval?(req: PlanApprovalRequest): Promise<PlanApprovalDecision>;
}
```

**`ipc.ts`** — 新增 plan 批准的 IPC 通道（照抄 `CLAUDE_RESPOND_QUESTION`）：
```ts
export const RespondPlanApprovalSchema = z.object({
  sessionId: z.string(),
  requestId: z.string(),
  approved: z.boolean(),
  editedPlan: z.string().optional(),
  reason: z.string().optional(),
});
export type RespondPlanApprovalInput = z.infer<typeof RespondPlanApprovalSchema>;

// IPC 常量
CLAUDE_RESPOND_PLAN_APPROVAL: "claude:respondPlanApproval",
// RpcMap
"claude.respondPlanApproval": (input: RespondPlanApprovalInput) => Promise<void>;
```

### 第2步：主进程后端

**`ApprovalBridge.ts`** — 新增第三个 Map（照抄 `pendingUserInputs`）：
```ts
private pendingPlanApprovals = new Map<string, PendingPlanApproval>();
makePlanApprovalHandler(sessionId, emit) { /* 照抄 makeUserInputHandler，emit plan.approval_request */ }
resolvePlanApproval(requestId, decision) { /* 照抄 resolveUserInput */ }
// rejectAll 里清空 pendingPlanApprovals
```

**`ClaudeAgentSdkProvider.ts`** — 在 `canUseTool` 里加 ExitPlanMode 分支（在 AskUserQuestion 分支之后）：
```ts
if (toolName === "ExitPlanMode") {
  if (!requestPlanApproval) return { behavior: "deny", message: "Plan approval unavailable" };
  const plan = readStr((input as any)?.plan);
  const decision = await requestPlanApproval({
    requestId: randomUUID(), plan, toolUseId: opts.toolUseID,
  });
  return decision.approved
    ? { behavior: "allow", updatedInput: { ...input, plan: decision.editedPlan ?? plan, message: "Plan approved by user" } }
    : { behavior: "deny", message: decision.reason ?? "Plan rejected by user" };
}
```
从 `ctx.requestPlanApproval` 解构（和 requestApproval/requestUserInput 并列）。

**`SdkMessageAdapter.ts`** — 在 `handleAssistant` 里识别 plan 工具调用发 `mode.change` 事件：
```ts
// 在现有 tool_use 发射逻辑后
if (b.name === "EnterPlanMode") {
  this.ctx.emit({ type: "mode.change", sessionId: this.sessionId, mode: "plan", source: "model" });
} else if (b.name === "ExitPlanMode") {
  // 注意：ExitPlanMode 被批准后 SDK 才会把它写进 finalized assistant message
  this.ctx.emit({ type: "mode.change", sessionId: this.sessionId, mode: "default", source: "model" });
}
```

**`RuntimeManager.ts`**：
- `ctx` 增加 `requestPlanApproval: approvalBridge.makePlanApprovalHandler(session.id, emit)`
- 新增 `resolvePlanApproval(requestId, decision)` 方法（照抄 `resolveUserInput`）

**`ipc/claude.ts`** — 新增 `CLAUDE_RESPOND_PLAN_APPROVAL` handler（照抄 119-144 行的 RESPOND_QUESTION，但无 sentinel 路径，直接调 `runtimeManager.resolvePlanApproval`）

### 第4步：renderer store（`sessionStore.ts`）

新增状态字段：
```ts
pendingPlanApproval: { sessionId: string; requestId: string; plan: string } | null;
pendingApproval: { sessionId: string; requestId: string; toolName: string; input: unknown; description?: string } | null;
effectiveMode: PermissionMode | null;  // 当前活动会话的实际模式（来自 mode.change 事件），null = 用 session.permissionMode
```

`ingestEvent` 新增分支：
- `mode.change` → `set({ effectiveMode: e.mode })`（source=model 时）；同时如果是 plan↔default 切换，可顺带更新 `permissionMode`（影响下一个会话默认值，可选）
- `plan.approval_request` → `set({ pendingPlanApproval: {...} })`
- `approval.request` → `set({ pendingApproval: {...} })`

新增 actions：
- `respondPlanApproval(approved, editedPlan?, reason?)` — 清卡片 + 调 IPC（照抄 `respondQuestion`）
- `respondApproval(granted, always?)` — 清卡片 + 调现有 `api.claude.approve`

### 第5步：新增 UI 组件

**新文件 `PlanApprovalPrompt.tsx`**（照抄 QuestionPrompt.tsx 的悬浮卡片样式）：
- 紫色主题卡片，渲染计划 Markdown（复用 `Markdown` 组件）
- 可编辑文本框（textarea，默认折叠，点"编辑"展开）—— 满足"支持编辑计划"
- [批准] [拒绝] 按钮 + 拒绝理由输入框（可选）
- 批准 → `respondPlanApproval(true, editedPlan)`；拒绝 → `respondPlanApproval(false, undefined, reason)`

**新文件 `ApprovalPrompt.tsx`**（通用工具审批悬浮框）：
- 琥珀色主题卡片（区别于 plan 的紫色和 question 的紫色）
- 显示 `toolName` + `description`（或 input 摘要）
- [允许] [允许并记住] [拒绝] 按钮
- 调用 `respondApproval`

**`ChatPane.tsx`** — 在 `<QuestionPrompt>` 旁边条件渲染新卡片（优先级：plan approval > question > general approval）：
```tsx
{activePlanApproval && <PlanApprovalPrompt ... />}
{activeQuestion && <QuestionPrompt ... />}
{activeApproval && <ApprovalPrompt ... />}
```

**`ComposerToolbar.tsx` + `StatusBar.tsx`** — 显示模式时优先用 `effectiveMode`（若活动会话有），fallback 到全局 `permissionMode`：
```ts
const effectiveMode = useSessionStore((s) => s.effectiveMode);
const displayMode = effectiveMode ?? permissionMode;
// chip 和 status bar 都用 displayMode
```

### 第6步：MessageBlocks 里 ExitPlanMode 特殊渲染（可选优化）

在 `toolSummary` 加 `case "ExitPlanMode": return "计划待批准"`，避免落到 default 把整个 plan JSON 显示在卡片标题。EnterPlanMode 同理显示"进入计划模式"。这部分是体验优化，非阻塞。

## 风险与备注

- **SDK 版本**：项目用 `^0.3.218`，非问题版本（2.0.51 是 claude-code CLI 的版本）。但仍对 `input.plan` 做 `readStr` 防御。
- **ExitPlanMode 在 finalized assistant message 里出现时机**：handleAssistant 收到时表示 SDK 已处理完批准流程（无论 allow/deny），此时发 `mode.change: default` 是安全的——若被拒绝，SDK 会继续在 plan 模式，但不会再次发 ExitPlanMode tool_use 给已拒绝的同一个。为避免误报，`mode.change` 以 `source: "model"` 标记，前端只在 source=model 时同步 effectiveMode。
- **持久化**：mode.change 不写回 SQLite 的 `session.permissionMode`（那是会话启动模式）。effectiveMode 是运行时状态，重启后从 session.permissionMode 重载。若希望批准计划后下个会话也用 default，可在批准时顺带 set permissionMode("default")，但这是产品决策，默认不做。
