# 中间面板 Tab 模式重构方案

## 一、目标

在保留现有"单会话替换"模式(默认)的同时,新增 **Tab 标签模式**:
- Tab 模式下,点击新会话(左栏)或新建会话(左下 +)会以 tab 标签形式追加到中间面板顶部;多个已开 tab 可来回切换继续查看;
- 切走的旧 tab 内,即使 Claude 正在运行(thinking / streaming / tool 执行),也**不受影响**;
- 通过"设置 → 外观"里的单选切换"单会话 / Tab 标签"模式,选择持久化到 SQLite `settings` 表。

## 四、实施方案

### 阶段 1:扩展 store —— 引入 tab 状态

**`apps/desktop/src/renderer/stores/sessionStore.ts`**

1. 新增 state 字段(行 69 后):
   - `openTabs: string[]` —— 已开 tab 的 sessionId 列表,**有序**;Tab 模式专用
   - `pendingQuestionBySession: Record<string, { questions: AskUserQuestionItem[] }>` —— 替代单 slot `pendingQuestion`
   - `turnFilesBySession: Record<string, TurnFileEntry[]>` —— 替代单 slot `turnFiles`

2. 删除:`pendingQuestion`(行 114)、`turnFiles`(行 124)单 slot 字段。`pendingApprovals` 保持数组(已天然多 session)。

3. 新增 actions:
   - `openTab(sessionId: string): Promise<void>` —— 核心入口。语义:
     - 若 `openTabs.includes(sessionId)`:只把 `activeSessionId` 切到它
     - 否则:push 到 `openTabs` 末尾 + `activeSessionId = sessionId`
     - 复用 `selectSession` 的"读 config + 拉历史"逻辑
   - `closeTab(sessionId: string): void` —— 从 `openTabs` 移除(无论是否 running);
     若关的是当前 active,**自动**切到 `openTabs[openTabs.length-1]`(若空则置 `null`)。
     **不**清理 `messagesBySession` / `runningBySession` / `turnFilesBySession` / `pendingQuestionBySession` —— 这些是"会话本体的状态",tab 关闭后下次再开仍可见。

4. 保留 `selectSession`(给单会话模式用),其内部去掉 `pendingApprovals: [] / pendingQuestion: null / turnFiles: []` 这种"全清"副作用 —— 单会话模式下切会话=换"焦点"即可,清不清桶不影响(本来就是按 sessionId 读)。

5. 改 `ingestEvent` 写入点:
   - 行 573-576 `question.ask`:`pendingQuestionBySession: { ..., [sid]: { questions: e.questions } }`
   - 行 588-604 `turn.files` / `turn.rewound`:`turnFilesBySession: { ..., [sid]: e.files }` / `[sid]: []`
   - 行 671-676 `error` 内的 `turnFiles: []` → `turnFilesBySession: { ..., [sid]: [] }`
   - `pendingApprovals` 已是数组,不动

6. 单会话模式 vs Tab 模式的 action 入口:
   - **LeftBar 调 `openTab`**(而不是 `selectSession`)
   - **左下 + 调 `startSession`** 后,自动 `openTab(newSessionId)`
   - 在 `openTab` / `startSession` 内部按当前 `displayMode` 决定"是否把 sessionId 加进 `openTabs`"**不**,而是这样:不论模式,**总是写 `openTabs` + 切 `activeSessionId`**;真正决定"是否用 tab 渲染"的是渲染层读取 `displayMode` 后:
     - `single` → 只渲染 `activeSessionId` 那个 ChatPane(等价于现在的行为)
     - `tabs` → 渲染 TabStrip + 多个 ChatPane,但只挂载 `activeSessionId` 那个(其他用 unmount 节省渲染;切回时再挂载 + 重读 store)
   - 这样 store 层只有"已开 tab"这一种状态,模式差异在渲染层体现,行为简单一致。

## 五、关键设计权衡

1. **为什么只在 active tab 挂载 ChatPane(而不是全部挂载 + display:none)?**
   - Composer 的本地 useState(草稿)即便不渲染也会"保留",但每个 ChatPane 内有大量 useSessionStore 订阅,tab 多时不必要的订阅。
   - `key={activeSessionId}` 重挂载简单可靠,符合现有"selectSession 重读 store"心智模型。
   - 代价:切回 tab 时滚动位置/草稿不保留(回到顶部);可接受,因为还有"会话历史持久化"兜底(草稿本地 useState 本来就不持久化)。

2. **为什么把单 slot 字段(pendingQuestion / turnFiles)改成 per-session 桶?**
   - 多 tab 同时跑 Claude 时,A 的 question.ask 不能覆盖 B 的。
   - main 进程 emit 出去的事件已经带 sessionId,改 store 写入是纯工作量。

3. **为什么不把 model / effort / permissionMode / customModelId 也按 sessionId 分桶?**
   - 改造成本大,要重写 ComposerToolbar、ModelDropdown、PermissionModeDropdown 三个组件的 selector。
   - 实际语义:这 4 个字段是"前台 tab 的偏好",已经由 `syncConfigFromSession` 同步,符合用户对 tab 切换的预期。
   - 留作后续优化。
